# tools/prepare

The launcher passes `--game DIR` for the chosen installation and `--runtime DIR` for the directory containing
`mkw`/`mkw.exe`. The package's tools stay in `setup/` beside the executable; compiled code, prepared files,
`setup-state.json`, logs and settings go into the installation. Without `--runtime`, it defaults to `--game`.

| Script | What it does | Usage |
|---|---|---|
| `prepare.py` | Prepares the game in the chosen installation folder from the player's copy: checks it is 1.0.0 (`main`'s build id, RomFS files), copies `exefs/` and copies or links `romfs/` (`mkw.ini`; a copy removes files the source dump does not have, so a folder set up from another version does not keep that version's), generates the C, builds it into `mkwgame.so`/`mkwgame.dll` with zig (or clang), translates the shaders to `spirv/` (as many processes as cores fit in free memory, 0.75 GB each; half as many again if one dies, issue #24) (the objects stay in `setup-work/obj` after the setup, keyed by their C, flags, compiler and headers: an update that changes a few functions compiles only their chunks, `gamecode.py`) and starts the game for a minute (no focus, no sound, with a separate profile) to leave the pipeline cache and its list ready for the first game. The internal resolution is not a step: it is the `MKW_RESOLUTION` option (`runtime/sdk/fs/romfs_res.c`). One event per output line (`step`, `progress`, `skip`, `done`, `error`) for the start screen; each step saves its key in `setup-state.json` and an interrupted setup resumes after the last step done. On Windows the link is `zig lld-link` with the package's prebuilt C runtime (`machine.py` `crt_link`): zig never builds its libc on the player's PC, the build that never ended on many of them (issue #2). The tools' output and the timings (zig's first link, the link) go to `logs/setup.log`; a link over 30 min stops with an error | From the start screen (Game files → Prepare); by hand: `python prepare.py --source DIR --game DIR [--romfs copy\|link]`; without `--source`, the last setup's copy and mode (after an update) |
| `update.py` | The start screen's update: `check` asks GitHub's `releases/latest` (published only, 5 s at most) whether a release is newer than this program; `fetch` downloads its package for this system with progress, checks its sha256 (GitHub's `digest`) and unpacks the Windows zip; `clean` removes the `*.old` files the launcher left after swapping (`runtime/ui/launcher/launcher_update.cpp`). TLS: the system's CA store, else pip's bundled one | From the start screen; by hand: `python -I update.py check --version 0.1.3`, `fetch --tag vX --dest DIR`, `clean --game DIR` |
| `nup.py` | Reads a Switch 2 `.nup` package (the dump as one file; layout in `runtime/sdk/fs/nup.c`): `prepare.py` checks it and extracts `exefs/` (and `romfs/` when copying; linked, the runtime reads the package in place), `tools/shaders/extract.py` reads its RomFS; packs a loose dump into one (`pack`, raw, read in place) and gives the dev tools one RomFS file or folder of a packed copy (`romfs_read`, `romfs_dir`) | Imported; by hand: `uv run tools/prepare/nup.py list GAME.nup`, `extract GAME.nup DIR [--part exefs\|romfs]`, `pack DIR GAME.nup --title 0400C3F00006E000 [--version N]` |
| `gamecode.py` | `prepare.py`'s compile step: the generated C into `mkwgame.so`/`mkwgame.dll` with the package's zig (or clang), a link probe beside the compiles and the link with its 30 min limit | imported by `prepare.py` |
| `gamecopy.py` | `prepare.py`'s copy of a loose `exefs/` or `romfs/` into the game folder: `COPY_JOBS` files at a time, resumable (a file already there with its size is kept, each written through `.part`); after any copy, loose, `.nup` or `.nx`, the files that version does not have are removed (#261), never in a linked folder or one holding the source | imported by `prepare.py` |
| `machine.py` | What `prepare.py`'s steps run with: the package's tools (`setup/` next to the executable) or the system's, the tool processes tied to the setup's (process group, Windows job object), and the memory that sizes the parallel jobs | Imported by `prepare.py` |
